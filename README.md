# Lineview
- A small multi-tenant factory-analytics app, built to measure Postgres Row-Level Security(RLS): what it costs, where it breaks, and whether the app can
still leak data around it.
- The repo is the test bench for the blog post (blog post)[https://...]. Everything runs on fake, seeded data, so you can rebuild it and reproduce on your
machine.
  - **Stack**: Go API, Postgres 18, Docker Compose, Locust for load tests.
  - **Auth is mock**: (no passwords or signup): every seeded user starts with one valid session. Real authentication is out of scope, since the isolation questions
    are the same either way
  - **Tokens in this repo are dev-only** Don't reuse them anywhere.

## The data
- Three fictional factories (tenants), deliberately very different sizes:

| Tenant | Users | Inspection Rows|
|--------|-------|----------------|
|Ironval Castings| 200|10,000, 000|
| Brightline Plastics| 100 | 2,7000,000|
|Kestrel Fasteners| 50 | 10,000|

- The data comes form fixed seeds, so row counts and aggregates are the same on every load. The UUIDs are different every time you load, so the commands below look tenants
up by name instead of hard-coding ids.

## Layout
```sh
docker-compose.yml          db, api, loader(profile "load"), locust(profile "load")
db/init                     01-roles.sql, 02-schema.sql, 03-auth.sql, 04-rls.sql
backend/cmd/loader/         data loader (writes loadtest/tokens.json)
backend/cmd/api/            the Go API
backend/internal/authtoken  token hashing
locust/                     locustfile.py (leak test), noisy.py (noisy neighbour test)
loadtest/                   generated by the loader, not in version control
```
- Three database roles: `dev_user` (superuser, bypasses RLS, used only by the loader), `lineview_app` (tenant data, subject to RLS), `lineview_auth` (reads only the auth schema).

## Requirements
- Docker with Compose v2. Go is built inside Docker, so you don't need it locally.
- Several GB of free disk and a few GB of RAM for Docker. The loader writes 12.7 million rows.
- `jq` and `curl` for the smoke tests.

## Quick start
1.**Start the database**. The scripts in `db/init` run only when the data volume is empty and `04-rls.sql` is one of them.
```sh
    docker compose up -d db
```
2. **Load the data**. This truncates everything adn reloads all 12.7M rows, so it takes a while.
```sh
    docker compose run --build --rm loader -reset
```
  - it writes `loadtest/tokens.json`. That file is the ***only copy for the plaintext session tokens***(the database stores hashes), so keep it. Losing it means a full reload.
3. **Check that RLS is on.** You want `t` and `t` on all four rows.
```sh
    docker compose exec -T db psql -U dev_user -d lineview_db -c \
    "SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class WHERE relname IN ('tenants', 'machines', 'products', 'inspection_results');"
```
4. **Start the API**(safe mode by default) and smoke-test it.
```sh
    docker compose up -d --build api
    curl -i localhost:8080/healthz                      # 200 ok
    curl -i localhost:8080/api/defect-rate/products     # 401, no session cookie
    TOKEN=$(jq -r '[.[] | select(.tenant=="Kestrel Fasteners")][0].token' loadtest/tokens.json)
    curl -s --cookie "session=$TOKEN" localhost:8080/api/defect-rate/products | jq '[.[].tenant_id] | unique'
```
  - The last command should print exactly one tenant_id.

## API settings (environment variables)
| Variable | Default | Meaning|
|----------|---------|--------|
| `APP_DATABASE_URL`| required | connection string for the `lineview_app` role |
| `AUTH_DATABASE_URL`|  required| connection string for the `lineview_auth` role |
| `TENANT_MODE` | `safe` | `safe`= per-request transaction; `unsafe`= the deliberate bug |
| `APP_MAX_CONNS`| `10`| size of the tenant-data connection pooling|
| `UNSAFE_GAP_MS` | `0`| unsafe mode only; simulated work between setting the tenant and querying|
|  `LISTEN_ADDR` | `:8080` | listen address|

- To change `TENANT_MODE`, `APP_MAX_CONNS` or `UNSAFE_GAP_MS` from your shell, the `api` service in `docker-compose.yml` must pass them through, eg `TENANT_MODE: ${TENANT_MODE:-safe}`.

## Reproducing the results
- You absolute times will differe, and these are single runs. The patterns should hold. Every command below is run from the project root.

### 1. Does RLS fix the forgotten filter?
- The query has no `WHERE tenant_id`. Run it as the app role, once with RLS on and once off. Switching RLS off takes a lock on the table, so stop the API and Locust first.
```sh
    docker compose exec -T db psql -U dev_user -d lineview_db <<'EOF'
    SELECT id AS ironvale FROM tenants WHERE name = 'Ironvale Castings' \gset
    
    \echo --- RLS ON
    BEGIN;
    SET LOCAL ROLE lineview_app;
    SELECT set_config('app.tenant_id', :'ironvale', true);
    SELECT count(DISTINCT tenant_id) AS tenants_visible, count(*) AS deformed_rows
      FROM inspection_results WHERE outcome = 'deformed';
    ROLLBACK;
    
    \echo --- RLS OFF
    BEGIN;
    ALTER TABLE inspection_results DISABLE ROW LEVEL SECURITY;
    SET LOCAL ROLE lineview_app;
    SELECT set_config('app.tenant_id', :'ironvale', true);
    SELECT count(DISTINCT tenant_id) AS tenants_visible, count(*) AS deformed_rows
      FROM inspection_results WHERE outcome = 'deformed';
    ROLLBACK;
    EOF
```
Expected: 1 tenant and 367,473 rows with RLS on; 3 tenants and 466,353 rows with it off. Both transactions rollback, so RLS is on again afterwards.

### 2. What happens when something goes wrong?
```sh
    docker compose exec -T db psql -U dev_user -d lineview_db <<'EOF'
    SELECT id AS ironvale FROM tenants WHERE name = 'Ironvale Castings' \gset
    SELECT id AS other FROM tenants WHERE name = 'Brightline Plastics' \gset
    
    \echo === 1. Superuser, no tenant set
    SELECT count(*) AS machines_visible, count(DISTINCT tenant_id) AS tenants_visible FROM machines;
    
    \echo === 2. App role, no tenant set
    BEGIN; SET LOCAL ROLE lineview_app;
    SELECT count(*) AS machines_visible FROM machines;
    ROLLBACK;
    
    \echo === 3. App role as Ironvale, inserting a row for another tenant
    BEGIN; SET LOCAL ROLE lineview_app;
    SELECT set_config('app.tenant_id', :'ironvale', true);
    INSERT INTO machines (tenant_id, machine_code, name) VALUES (:'other', 'DEMO-1', 'wrong tenant');
    ROLLBACK;
    
    \echo === 4. Same insert, own tenant
    BEGIN; SET LOCAL ROLE lineview_app;
    SELECT set_config('app.tenant_id', :'ironvale', true);
    INSERT INTO machines (tenant_id, machine_code, name) VALUES (:'ironvale', 'DEMO-2', 'right tenant');
    ROLLBACK;
    EOF
```
- Expected: 61 machines across 3 tenant; 0 rows (no error); an error saying the new row violates the row-level security policy;and a successful insert. Check 3 fails with an error, which is the point.


### 3: What does RLS cost?
- The query is the defect rate per product over Ironvals's rows. Each variant below changes one thing. Run each one twice adn read the second result: the first warms the cache. In the plan, look at Execution Time, whether there is a **Gather** node with **Workers Lauchned**, adn the **Filter:** line.
- First save a helper script. It sets teh tenant and runs the plan as teh app role:
```sh
    cat > /tmp/cost.sql <<'SQL'
    SELECT id AS ironvale FROM tenants WHERE name = 'Ironvale Castings' \gset
    BEGIN;
    SET LOCAL ROLE lineview_app;
    SELECT set_config('app.tenant_id', :'ironvale', true);
    EXPLAIN (ANALYZE, BUFFERS)
    SELECT tenant_id, product_id, count(*), count(*) FILTER (WHERE outcome = 'deformed')
      FROM inspection_results
     WHERE inspected_at >= '1970-01-01' AND inspected_at < now() + interval '1 day'
     GROUP BY tenant_id, product_id;
    ROLLBACK;
    SQL
```
#### Variant A: **the naive policy** (helper function unlabelled, plain call)
```sh
    docker compose exec -T db psql -U dev_user -d lineview_db <<'EOF'
    ALTER FUNCTION public.current_tenant() PARALLEL UNSAFE;
    DROP POLICY IF EXISTS tenant_isolation ON inspection_results;
    CREATE POLICY tenant_isolation ON inspection_results TO lineview_app
      USING (tenant_id = public.current_tenant())
      WITH CHECK (tenant_id = public.current_tenant());
    EOF
    docker compose exec -T db psql -U dev_user -d lineview_db < /tmp/cost.sql
```
Expected: a single process, no Gather, and the slowest time.

#### Variant B: **label the function** `PARALLEL SAFE`
```sh
docker compose exec -T db psql -U dev_user -d lineview_db -c "ALTER FUNCTION public.current_tenant() PARALLEL SAFE;"
docker compose exec -T db psql -U dev_user -d lineview_db < /tmp/cost.sql
```
Expected: a Gather node with 2 workers, a much shorter time.

#### Variant C: also wrap the call in `(SELECT ...)`.
```sh
docker compose exec -T db psql -U dev_user -d lineview_db <<'EOF'
DROP POLICY IF EXISTS tenant_isolation ON inspection_results;
CREATE POLICY tenant_isolation ON inspection_results TO lineview_app
  USING (tenant_id = (SELECT public.current_tenant()))
  WITH CHECK (tenant_id = (SELECT public.current_tenant()));
EOF
docker compose exec -T db psql -U dev_user -d lineview_db < /tmp/cost.sql
```
Expected: an `initPlan` appears and the Filter line no longer contains `current_settings`.

#### Baseline: RLS off with an explicit filter (stop the API and Locust first):

```sh
docker compose exec -T db psql -U dev_user -d lineview_db <<'EOF'
SELECT id AS ironvale FROM tenants WHERE name = 'Ironvale Castings' \gset
BEGIN;
ALTER TABLE inspection_results DISABLE ROW LEVEL SECURITY;
SET LOCAL ROLE lineview_app;
EXPLAIN (ANALYZE, BUFFERS)
SELECT tenant_id, product_id, count(*), count(*) FILTER (WHERE outcome = 'deformed')
  FROM inspection_results
 WHERE tenant_id = :'ironvale'
   AND inspected_at >= '1970-01-01' AND inspected_at < now() + interval '1 day'
 GROUP BY tenant_id, product_id;
ROLLBACK;
EOF
```
- **Selective query (7-day window)**. Repeat the RLS-on helper and the baseline with `inspected_at >= '2026-06-01' AND inspected < '2026-06-08'` in place of the all-time range.
- With variant C installed, I saw an index scan that was several times slower than the baseline. To test whether the plan choice is the cause, add these two lines after
`SET LOCAL ROLE lineview_app;` in the RLS-on helper:
```sh
SET LOCAL enable_indexscan = off;
SET LOCAL enable_bitmapscan = off;
```
- That forces a sequential scan and should bring the time close to the baseline. It's a diagnostic, not something to set in production.
- **Restore the final policy** when you're done, by reapplying the init file (it's safe to run it run it again):
```sh
docker compose exec -T db psql -U dev_user -d lineview_db -v ON_ERROR_STOP=1 < db/init/04-rls.sql
```

### 4: Can the app leak data? (Locust)
- The load test logs in as real seeded users, and flag every response that contains a row form another tenant as a `LEAK`.Run it in both modes under the same load.
- **Dont set `TENANT_MODE` on on command and run the test in another.** `docker compose run` recreates `api` service if it differs from its configuration, and without the variable it comes back in safe mode. Always pass `--no-deps` to `run`, and check the mode in the log before and after:
```sh
    docker compose logs api | grep listening | tail -1
```
- Both lines must show the same mode and the same timestamp. A different timestamp means the API restarted during the run, so discard it.
**Matched Pair**(Kestrel and Brightline only, 100 users, 1-day windows, almost no think time):
```sh
# Unsafe
TENANT_MODE=unsafe docker compose up -d --force-recreate api
docker compose logs api | grep listening | tail -1
docker compose --profile load run --rm --no-deps \
  -e TENANTS="Kestrel Fasteners,Brightline Plastics" -e WAIT_MIN=0 -e WAIT_MAX=0.05 -e WINDOW_DAYS=1 \
  locust -f /mnt/locust/locustfile.py --host http://api:8080 --headless -u 100 -r 50 -t 60s --only-summary
docker compose logs api | grep listening | tail -1

# safe (the control)
TENANT_MODE=safe docker compose up -d --force-recreate api
docker compose logs api | grep listening | tail -1
docker compose --profile load run --rm --no-deps \
  -e TENANTS="Kestrel Fasteners,Brightline Plastics" -e WAIT_MIN=0 -e WAIT_MAX=0.05 -e WINDOW_DAYS=1 \
  locust -f /mnt/locust/locustfile.py --host http://api:8080 --headless -u 100 -r 50 -t 60s --only-summary
docker compose logs api | grep listening | tail -1
```
Expected: in unsafe mode, about half teh requests report a `LEAK` (my run: 49%), and in safe mode, none. Latency looks the same in both, which is part of the point.
The leak comes from teh unsafe mode's two separate trips to the connection pool: it sets the tenant on one checkout and queries on another, and under load the second one gets whichever connection frees up next. The log line's `tenant_mode` field tells you which mode a run used.

Locust settings (environment variables read by `locustfile.py`): `TENANTS`(comma-separated tenant names), `WAIT_MIN/WAIT_MAX`(think time in seconds), `WINDOW_DAYS`(query window), `TOKENS_PATH`

### 5. Noisy neighbour
- A light tenant (Kestrel, 3 users) alone, then next to a heavy one (IronVal, 20 users). Safe mode. Compare only the `victim [Kestrel fasteners]` row.
```sh
    TENANT_MODE=safe docker compose up -d --force-recreate api
    docker compose logs api | grep listening | tail -1
    
    # Phase A: victim alone
    docker compose --profile load run --rm --no-deps \
      -e VICTIM_USERS=3 -e NEIGHBOUR_USERS=0 \
      locust -f /mnt/locust/noisy.py --host http://api:8080 --headless -u 3 -r 3 -t 60s --only-summary
    
    # Phase B: victim plus a heavy neighbour
    docker compose --profile load run --rm --no-deps \
      -e VICTIM_USERS=3 -e NEIGHBOUR_USERS=20 \
      locust -f /mnt/locust/noisy.py --host http://api:8080 --headless -u 23 -r 23 -t 60s --only-summary
```
`-u` must equal the sum of the two user count. 
**Expected**: Kestrel's median goes from about 10ms to a few seconds, with no errors. I haven't separated "waiting for  connection" from "the database's CPU" yet; running phase B with a larger `APP_MAX_CONNS` is the first thing to try.

## Troubleshooting
- `permission denied` writing `tokens.json`: this didn't happen on a clean clone my machine, where the loader created the folder itself. If you hit it, check who owns `loadtest/` (`ls -ld loadtest`) and make sure it writable for the user the loaders runs as.
- **Changed `db/init/*.sql` and nothing happened**: init scripts only run on an empty volume. Apply the file by hand with `psql`, or wipe everything with `docker compose down -v` (this deletes the loaded data).
- `tokens.json not found` **from locust**: run the loader first.
- **A Locust run reports 0 leak in unsafe mode**: check the `listening` log lines. Almost certainly the API was recreated in safe mode.
- **Different numbers from mine**: expected, Timing depends on your hardware,Docker, and what else is running. The row count in section 1 should match exactly.
